Customer enablement

Onboarding qURL Connector with attested state providers

A field-ready onboarding guide for customers deploying qURL Connector with AWS Nitro or Google Cloud Confidential Space key custody. Use this to plan the rollout, configure cloud policy, complete first native registration, and hand the deployment to operations.

1. Outcomes

The goal is a qURL Connector deployment where its complete native identity, assigned-cell endpoint, and device credential are never stored as durable plaintext. The Connector stores one qurl-go state envelope whose random data-encryption key is wrapped by the attested provider.

Maintainer note This guide is intentionally standalone HTML so it can be handed to customers as a single print-friendly artifact. When updating it, re-check the source-of-truth env-var contract in docs/install-docker.md and the provider gates in pkg/agentstate. For customer distribution, send a rendered or downloaded HTML artifact, not the GitHub source view.

What success looks like

  • The customer can start the qURL agent without keeping QURL_API_KEY in steady state.
  • The persistent state directory contains agent_state.sealed.json, not split identity or TOML files.
  • Replacement instances can unseal only when cloud attestation policy matches the approved workload.
  • Cloud audit logs show the expected KMS encrypt/decrypt calls and no unexpected principal can decrypt.

What this does not do

  • It does not remove the need for cloud IAM or KMS policy review.
  • It does not make the local GCP token parse a cryptographic verifier.
  • It does not make AWS first seal host-compromise-resistant if first seal runs in the parent host process.
  • It does not treat the NHP public key as secret; this guide protects private-key custody and durable private-key state.
  • It does not replace first native UDP registration through the pinned LayerV Hub.
Definition of done The customer has completed the provider-specific policy gate, performed a greenfield native UDP registration, restarted without the enrollment credential, verified Connector connectivity, and documented rollback ownership.

2. Architecture model

qurl-go owns the stable X25519 identity, Hub-provided cell assignment, and device credential. With a sealed provider, the persistent volume stores one encrypted complete-state envelope. The provider unwraps only the envelope DEK; no rendered runtime TOML or split key file exists.

Provider tiers

Provider tiers and customer security posture
Tier Provider Customer posture Typical use
Baseline file Complete plaintext agent_state.json in the state directory. Development or low-sensitivity local deployments.
Tier 1 aws-kms, gcp-kms KMS envelope encryption, but no attested release condition. Customers who need sealed state but do not run in attested compute.
Tier 2 aws-nitro, gcp-confidential-space Key release is tied to cloud attestation policy and matching workload identity. Production workloads with stronger key-custody requirements.
The security boundary is cloud policy. The qURL client fails closed and checks local configuration, but the actual confidentiality boundary is the AWS KMS key policy for Nitro or the GCP Workload Identity Federation/IAM binding for Confidential Space. A misconfigured cloud binding can silently downgrade the deployment.

Ask the customer to complete this worksheet before implementation. Do not start the deployment until the security owner and platform owner agree on the provider and validation gates.

4. Choose the provider

Pick exactly one key provider per state volume. Provider selection is bound to the envelope already on disk: file may open only agent_state.json, while KMS and attested providers may open only agent_state.sealed.json. Switching a non-empty volume fails closed. Use an empty mode-0700 state directory and a new enrollment when changing providers.

Choose AWS Nitro when

  • The workload runs in AWS Nitro Enclaves or NitroTPM-backed attested runtime.
  • The customer can enforce kms:RecipientAttestation:* conditions on the KMS key.
  • The customer has an attested unwrap helper inside the runtime.
  • The first seal can happen in the attested runtime or a tightly controlled provisioning window.

Choose GCP Confidential Space when

  • The workload runs in Google Cloud Confidential Space.
  • The customer can bind Workload Identity Federation and Cloud KMS IAM to the same image and service-account claims.
  • The container has access to the Confidential Space attestation token file.
  • The customer is prepared to validate IAM with a negative test before production enablement.
Do not mix install paths. Use either the container path or binary/service path for one host and one state volume. Running two agents against the same state directory creates competing Connector registrations for the same agent identity.

5. AWS Nitro onboarding

aws-nitro uses normal KMS encrypt for first seal, then requires KMS Recipient decrypt on unseal. AWS KMS returns CiphertextForRecipient instead of host plaintext when the decrypt request includes a signed attestation document. The qURL client fails closed if AWS returns host plaintext.

AWS prerequisites

  • A customer-managed AWS KMS key in the target region.
  • An IAM principal for first native registration with kms:Encrypt.
  • A steady-state decrypt principal constrained by KMS Recipient Attestation conditions.
  • An attestation document generated for the current process start.
  • An unwrap helper that runs inside the attested runtime, reads CiphertextForRecipient from stdin, and writes exactly the 32 raw state-envelope DEK bytes to stdout with no trailing newline.

Recommended AWS key-policy shape

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowQurlAgentFirstSeal",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/qurl-agent-provisioner"
      },
      "Action": "kms:Encrypt",
      "Resource": "*"
    },
    {
      "Sid": "AllowQurlAgentNitroDecrypt",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/qurl-agent-parent"
      },
      "Action": "kms:Decrypt",
      "Resource": "*",
      "Condition": {
        "StringEqualsIgnoreCase": {
          "kms:RecipientAttestation:ImageSha384": "PCR0_OR_IMAGE_SHA384_HEX"
        }
      }
    }
  ]
}
Treat this as a KMS key policy, not an IAM identity policy. In a key policy, "Resource": "*" refers to the current KMS key; do not copy these statements into a broad identity policy without replacing the resource with the exact key ARN.

Use additional kms:RecipientAttestation:PCR<PCR_ID> conditions when the customer wants PCR1, PCR2, or custom PCR binding. AWS documents Nitro Enclaves KMS attestation condition keys in Condition keys for Nitro Enclaves. AWS KMS Decrypt with Recipient returns the encrypted result in CiphertextForRecipient; see the AWS KMS Decrypt API reference.

AWS environment contract

LAYERV_KEY_PROVIDER=aws-nitro
LAYERV_AWS_KMS_KEY_ID=arn:aws:kms:us-east-1:111122223333:key/...
LAYERV_AWS_KMS_REGION=us-east-1
LAYERV_AWS_NITRO_ATTESTATION_DOCUMENT_FILE=/run/qurl/attestation.cose
LAYERV_AWS_NITRO_ATTESTATION_DOCUMENT_ENCODING=raw
LAYERV_AWS_NITRO_RECIPIENT_UNWRAP_COMMAND=/opt/qurl/bin/unwrap-recipient
QURL_API_KEY_FILE=/run/secrets/qurl-api-key
LAYERV_AGENT_ID=customer-prod-agent-01

The unwrap command is split on whitespace without shell or quote parsing. Use an executable path and arguments that do not contain spaces.

AWS implementation steps

  1. Create or select the KMS key and apply the first-seal and recipient-decrypt policy.
  2. Build the attested runtime image with the qURL client and unwrap helper.
  3. Generate the Nitro attestation document for the current process start and mount it at the configured path.
  4. Start qURL Connector with LAYERV_KEY_PROVIDER=aws-nitro and the enrollment credential mounted.
  5. Confirm agent_state.sealed.json exists and no legacy split state remains.
  6. Restart without the enrollment credential and confirm the Connector reconnects through attested unseal.
  7. Remove or narrow kms:Encrypt if first seal happened in a separate provisioning role.
First-seal caveat AWS KMS Encrypt has no Recipient mode. First seal generates the complete native state in the qURL agent process before KMS encrypts its envelope key. Run first seal inside the attested runtime whenever possible. If a separate provisioning window is required, keep it tightly controlled and remove encrypt permission from steady-state roles afterward.

6. GCP Confidential Space onboarding

gcp-confidential-space validates local Confidential Space token claims before Cloud KMS calls, but the local parse is not a JWT verifier. The real key-release gate is Workload Identity Federation, IAM policy, and Cloud KMS.

GCP prerequisites

  • A Cloud KMS key that the federated Confidential Space workload can use.
  • A Workload Identity Pool and OIDC provider for the Confidential Space attestation token.
  • An attribute mapping that exposes the approved image digest and other required claims.
  • An attribute condition that requires swname == 'CONFIDENTIAL_SPACE', stable support attributes, and the approved image or service-account claims.
  • The qURL container must be able to read the Confidential Space token file, defaulting to /run/container_launcher/attestation_verifier_claims_token.
Mandatory GCP warning The qURL local checks are advisory. If the customer does not enforce the same image digest and service-account claims in WIF/IAM, forged local token-file claims can pass startup while Cloud KMS still releases the key. Treat the negative IAM test as a production gate.

Recommended GCP WIF and KMS shape

gcloud iam workload-identity-pools providers create-oidc attestation-verifier \
  --location=global \
  --workload-identity-pool=QURL_AGENT_POOL \
  --issuer-uri="https://confidentialcomputing.googleapis.com" \
  --allowed-audiences="https://sts.googleapis.com" \
  --attribute-mapping="google.subject=\"gcpcs::\"+assertion.submods.container.image_digest+\"::\"+assertion.submods.gce.project_number+\"::\"+assertion.submods.gce.instance_id,attribute.image_digest=assertion.submods.container.image_digest" \
  --attribute-condition="assertion.swname == 'CONFIDENTIAL_SPACE' && 'STABLE' in assertion.submods.confidential_space.support_attributes && assertion.submods.container.image_digest == 'sha256:...'"

gcloud kms keys add-iam-policy-binding \
  projects/example-project/locations/us/keyRings/qurl/cryptoKeys/agent-identity \
  --member="principalSet://iam.googleapis.com/projects/123456789/locations/global/workloadIdentityPools/QURL_AGENT_POOL/attribute.image_digest/sha256:..." \
  --role=roles/cloudkms.cryptoKeyEncrypterDecrypter

Google documents Confidential Space attestation assertions, including swname, dbgstat, container image attributes, and support attributes, in the Confidential Space attestation assertions reference. The token claim payload includes google_service_accounts and default audience guidance in the Confidential Space token claims reference. Google also documents WIF attribute conditions in the Workload Identity Federation documentation.

GCP environment contract

LAYERV_KEY_PROVIDER=gcp-confidential-space
LAYERV_GCP_KMS_KEY_NAME=projects/example-project/locations/us/keyRings/qurl/cryptoKeys/agent-identity
LAYERV_GCP_CONFIDENTIAL_SPACE_TOKEN_FILE=/run/container_launcher/attestation_verifier_claims_token
LAYERV_GCP_CONFIDENTIAL_SPACE_IMAGE_DIGEST=sha256:...
LAYERV_GCP_CONFIDENTIAL_SPACE_SERVICE_ACCOUNT=qurl-agent@example-project.iam.gserviceaccount.com
QURL_API_KEY_FILE=/run/secrets/qurl-api-key
LAYERV_AGENT_ID=customer-agent-01

GCP implementation steps

  1. Create or select the Cloud KMS key.
  2. Create the Workload Identity Pool provider with attribute mapping and a restrictive attribute condition.
  3. Grant Cloud KMS access only to the federated principal that matches the approved image digest and service account.
  4. Start the qURL client in Confidential Space with LAYERV_KEY_PROVIDER=gcp-confidential-space.
  5. Confirm startup logs show the local attestation check passed and that key release is enforced by WIF/IAM.
  6. Confirm agent_state.sealed.json exists and the Connector connects.
  7. Run a negative policy test using a mismatched image digest or service account before production enablement.

7. Native registration

qurl-go persists the complete sealed state only after the configured provider wraps its random DEK. Registration and assignment occur directly over UDP through the pinned LayerV Hub; there is no HTTP registration or assignment call.

New deployment

  1. Mount the LayerV enrollment credential as a file and set QURL_API_KEY_FILE.
  2. Set a stable LAYERV_AGENT_ID for the deployment.
  3. Set the provider-specific environment variables.
  4. Start the Connector and wait for Hub registration, cell assignment, assigned-cell completion, and Connector connection.
  5. Restart without QURL_API_KEY_FILE and confirm the agent reconnects from persisted state.

Greenfield state requirement

No in-place migration or provider switch Native UDP builds reject legacy split state, both native envelopes together, and an envelope that does not match LAYERV_KEY_PROVIDER before writing anything. Archive the old volume when required, provision an empty mode-0700 state directory, and perform an explicit new enrollment.
  1. Back up the state volume according to the customer's policy.
  2. Provision an empty state directory owned by the Connector runtime UID with mode 0700.
  3. Set LAYERV_KEY_PROVIDER and its provider-specific inputs.
  4. Start with the enrollment credential and confirm native UDP registration succeeds.
  5. Confirm agent_state.sealed.json exists, then restart without the enrollment credential.

8. Validation plan

The customer should complete all validation before the rollout is considered production-ready. Capture evidence in the customer's change ticket.

Phase A: startup and state

  • Agent starts with the selected provider and exits non-zero if required provider env is missing.
  • State directory contains exactly one agent_state.sealed.json complete-state envelope.
  • State directory contains no legacy split key, identity-cache, or rendered TOML artifacts.

Phase B: Connector behavior

  • Agent registers or loads the expected LAYERV_AGENT_ID.
  • Routes connect through qURL Connector and survive an agent restart.
  • Restart without the enrollment credential succeeds from sealed persisted state.
  • Removing or corrupting required attestation inputs causes startup failure before the Connector establishes a connection.

Phase C: cloud policy gates

  • AWS: approved attestation decrypt succeeds and returns CiphertextForRecipient, not host plaintext.
  • AWS: an unapproved image digest or PCR cannot decrypt.
  • GCP: approved Confidential Space workload obtains KMS access.
  • GCP: a non-attested principal, wrong image digest, or wrong service account cannot decrypt.
  • CloudTrail or Cloud Audit Logs show only expected KMS operations during rollout.

Useful local checks

These examples use the default state dir. If the deployment sets LAYERV_AGENT_STATE_DIR, replace /var/lib/layerv/agent with that path. 

# Confirm sealed state
ls -la /var/lib/layerv/agent
test -f /var/lib/layerv/agent/agent_state.sealed.json
test ! -e /var/lib/layerv/agent/private_key
test ! -e /var/lib/layerv/agent/etc/config.toml

# Confirm the provider recorded in the sealed blob
grep -m1 -E '"provider"[[:space:]]*:[[:space:]]*"(aws-nitro|gcp-confidential-space)"' \
  /var/lib/layerv/agent/agent_state.sealed.json

# Confirm steady-state restart does not need the enrollment credential
# Remove QURL_API_KEY / QURL_API_KEY_FILE from compose or service env first.
docker compose up -d --force-recreate qurl-agent

9. Operations handoff

After onboarding, transfer these operating notes to the customer's runbook owner.

Operations handoff topics
Topic Operational guidance
API key handling Keep the enrollment credential available only for first native registration or deliberate reprovisioning. Remove it from steady-state runtime when sealed state is confirmed.
State volume Do not delete or share the state volume. It contains the stable identity, device credential, assignment, and sealed complete-state envelope.
Key rotation Coordinate KMS key policy changes with qURL restarts. Replacement instances need the same attestation policy and access to the sealed blob.
AWS attestation document Regenerate for each process start. Keep it paired with the recipient key held by the attested unwrap runtime.
GCP token file The client revalidates the token before KMS calls. Expired, debug, non-stable, wrong-image, or wrong-service-account tokens fail startup or unseal.
Audit Review AWS CloudTrail or GCP Cloud Audit Logs for unexpected decrypt attempts, principals, image digests, or policy condition failures.
Rollback Rollback only to a native-envelope-compatible workload using the unchanged matching-provider state. A pre-native build requires a separate empty volume and new enrollment.

Customer acceptance checklist

  • Customer security owner approved the cloud KMS policy and negative tests.
  • Customer platform owner confirmed restart behavior without the API key.
  • Customer operations owner accepted the troubleshooting and rollback notes.
  • LayerV owner confirmed qURL Connector connectivity and expected agent ID.
  • Evidence links are attached to the customer change ticket.

10. Troubleshooting

Troubleshooting symptoms and actions
Symptom Likely cause Action
Startup says provider requires an env var. Required provider configuration is missing. Set the provider-specific env vars listed in this guide. For GCP, image digest and service account are required before the token file is read.
AWS unwrap helper fails or returns wrong-size plaintext. Helper is not running in the attested runtime, writes text/newline, or emits too much stdout. Verify the command path, stdin/stdout contract, and that stdout is exactly 32 raw bytes.
AWS KMS returns host plaintext. Recipient decrypt is not being enforced or the request did not include valid attestation. Fix the key policy and attestation document. The client intentionally rejects host plaintext for aws-nitro.
GCP startup says token is expired. The Confidential Space token is stale beyond the 30-second leeway. Refresh the workload/token source and restart. Validate system clock behavior if it repeats.
GCP startup says dbgstat is not disabled. The workload is running in a debug configuration. Use production Confidential Space settings with debug disabled since boot.
GCP local checks pass, but KMS decrypt fails. WIF/IAM binding, principalSet, service account, or Cloud KMS permission does not match. Compare local pins to the WIF attribute mapping and Cloud KMS IAM binding. Confirm the federated principal matches the approved workload.
Agent asks for API key after restart. State volume is missing, not mounted, or belongs to a different agent. Restore the correct persistent state directory or intentionally perform a new native enrollment.
Escalation packet When escalating to LayerV, include the selected provider, redacted environment contract, agent ID, state directory listing, relevant startup logs, KMS key policy or IAM binding summary, and cloud audit event IDs. Do not send raw API keys, private keys, attestation private keys, or full unredacted customer IAM credentials.
